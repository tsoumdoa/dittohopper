Question 2

Match simply by ID, or something more durable?

Use Rhino GUIDs as the first signal, but never the only one. They survive edits made in place. They don't survive the things GH users do all day.

✓GUID survives

  • Move, Rotate, Scale, Gumball
  • Control-point and sub-object edits
  • Changing layer, name, color or user text
  • Save, Save As, reopening the file

✕GUID is lost (new object)

  • Re-baking from Grasshopper (delete, then bake again)
  • Join, Explode, Booleans, Copy or Mirror then deleting the original
  • Round-trips through DWG, IFC or other tools
  • A consultant rebuilding or re-exporting the model

    The durable version: a matching cascade

    Each pass only sees objects no earlier pass claimed. Cheap, certain signals go first and fuzzy ones last. Example numbers: a 1,240-object model after a partial re-bake.

    Three rules that keep it trustworthy

    Identity ≠ change
    Matching decides which object is which. Comparing decides what changed. A pair matched by geometry hash has unchanged geometry by definition, so only its attributes can differ.
    Every pair carries evidence
    Store matchedBy and confidence on each pair and show them in the UI. Users can unlink or relink pairs. Low-confidence pairs go into a "review" bucket instead of being presented as certain.
    Opt-in: stamp a durable key
    A Stamp IDs component writes diff:uid into user text. Bakes that carry it forward make pass 1 catch almost everything. It's opt-in because it writes to the model.
