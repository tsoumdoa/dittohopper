Question 1

Does it even make sense as a Grasshopper plugin?

Partly. GH works well for running diffs automatically and as the first thing you ship. It's a poor place to review 300 changes. Keep the diff engine free of any UI so GH and a Rhino panel can share it.

Suggested shape: one engine (a plain .NET library on RhinoCommon) with GH components first (v0), a dockable Rhino panel for review next (v1), and headless runs later.

GH works well for

  • Computational designers already work there, so there's no new tool to learn.
  • The diff is data. Added and moved objects can go into filters, tags, bakes and reports.
  • Rule-based QA, e.g. "fail if anything on Structure::* changed".
  • It's the fastest way to iterate on the matching logic itself.

GH is awkward for

  • Review means browsing a list and zooming to things. The canvas is built for data flow, not that.
  • On big models every upstream tweak re-runs the diff, so snapshots must be cached.
  • Preview is tied to each component: you can't click a row to zoom to it, and selection doesn't sync.
  • Modelers and PMs who never open GH can't use it.
